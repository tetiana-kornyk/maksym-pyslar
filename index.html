QA-IDP-04 Databases & SQL — reading and reasoning about data Medium
NOT STARTED ▾
Starting point
Databases & SQL came in at 2.0 — both sub-areas equal, theory present, one stretch of practice a long time ago. Worth being clear about the cause: the projects you have been on have not given you much database work, so this is not a case of neglecting something that was available to you, and the next one may not give you any either. That is why this case is deliberately almost entirely theoretical. The aim is not fluency at writing queries — it is that you can read one a developer shows you and say what it returns, know what belongs in a database and what a screen will never reveal, and ask the right question when something looks wrong. That knowledge pays off even when someone else runs the query. With the API layer from case 01 in your hands, it is the other half of the same picture: a response with the right shape and the wrong data is only explainable from the data side.
Steps to learn
Expected result
Describes how a relational database is structured and can sketch which tables a familiar flow touches. Names what each key and constraint prevents, and what each join type returns. Reads a query he is shown and says what it will return. Separates relational from non-relational and what that changes for a tester. Lists what a database holds that no screen reveals, and knows how SQL-prepared test data would help. Has asked for read-only access where the project allows it, or arranged a route to a developer for data questions where it does not — and either way can frame the question precisely enough to be useful.
Resources
Suggested: sqlbolt.com — short, browser-based, and worth working through for the reading skill even though nothing here requires it · Learning SQL (Beaulieu), first chapters, for structure and constraints · the schema of a product you test, if anyone will walk you through it once
